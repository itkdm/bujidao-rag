# AGENTS.md 全局规范

`AGENTS.md` 用于记录项目中需要开发者和 Coding Agent 长期遵守的项目级上下文、执行规则和约束。

只记录**长期有效、可重复使用**的信息。

不要将以下内容写入 `AGENTS.md`：

* 单次需求的临时要求
* 一次调试过程中得到的临时结论
* 尚未确认的猜测
* 已经由其他全局规范统一规定、且当前项目没有差异的重复内容
* 可以直接从代码中稳定获取、且没有额外说明价值的大量实现细节

---

## 一、默认位置【必选】

项目级 `AGENTS.md` 默认放在项目根目录：

```text
./AGENTS.md
```

当项目规模较大，且某个子目录存在独立、长期有效的局部约束时，可以在对应子目录增加：

```text
{sub-directory}/AGENTS.md
```

不要为了目录完整性批量创建子级 `AGENTS.md`。

只有存在真实局部规则时才创建。

---

## 二、指令范围与优先级【必选】

执行任务时遵循以下原则：

1. 用户当前明确要求优先于项目默认规则。
2. 根目录 `AGENTS.md` 作用于整个项目。
3. 子目录 `AGENTS.md` 只作用于其所在目录及子目录。
4. 多级 `AGENTS.md` 同时生效时，作用范围更具体的规则优先。
5. 子级规则只记录局部差异，不应重复复制根级规则。
6. 不确定规则是否仍然有效时，应检查当前项目、代码和相关正式文档，不根据历史经验猜测。

---

## 三、编写与更新原则【必选】

### 3.1 只记录已确认信息

写入内容必须至少满足以下一种条件：

* 可以通过当前项目文件或代码确认；
* 可以通过正式项目文档确认；
* 由用户或项目负责人明确确认。

禁止将推断直接写成长期规则。

---

### 3.2 保持长期有效

`AGENTS.md` 应优先记录：

* 项目基本定位
* 稳定技术栈
* 目录与模块职责
* 开发、运行和验证方式
* 项目特有工程约束
* 项目特有编码约定
* Agent 必须遵守的限制
* 容易反复踩坑的稳定风险
* 与团队全局规范不同的项目级规则

不要记录：

* 当前需求进度
* 临时 TODO
* 本次修改涉及哪些文件
* 一次性的调试命令
* 临时测试结果
* 某次任务的分析过程

---

### 3.3 优先增量维护

已有 `AGENTS.md` 时：

* 优先修改已有相关章节；
* 避免重复新增表达相同含义的规则；
* 已失效内容应直接更新或删除；
* 不通过不断追加“补充说明”保留已经过期的规则。

---

### 3.4 不确定内容不进入正式规则

如果某项信息尚未确认：

* 优先继续检查项目；
* 无法确认时不要写入；
* 必须暂时保留时，可明确标记为 `待确认`，并尽快完成验证。

---

## 四、AGENTS.md 推荐结构

以下结构分为**必选章节**与**可选章节**。

必选章节应在项目实际存在对应信息时维护完整。

可选章节只有在项目确实存在相关长期规则时才添加。

不要为了套用结构创建大量空章节。

---

# AGENTS.md

## 项目概述【必选】

用于让开发者和 Agent 快速判断当前项目是什么。

建议包含：

* 项目名称
* 项目目标 / 核心职责
* 当前主要形态
* 多应用或单应用情况
* 其他理解项目必须知道的基础信息

内容应保持简洁，不写产品宣传性质介绍。

---

## 技术栈【必选】

记录当前项目实际使用的主要技术。

根据项目类型按需填写，例如：

* 前端
* 后端
* 数据库
* 缓存
* 消息队列
* 构建工具
* 测试框架
* 关键基础设施
* 其他重要依赖

只记录会影响开发决策的主要技术，不需要罗列所有依赖。

---

## 目录与模块职责【必选】

说明项目主要目录、模块及其职责。

重点回答：

> 修改某类功能应该优先进入哪里？

例如说明：

* 主要应用目录
* 核心业务模块
* 公共模块
* 基础设施模块
* 测试目录
* 配置目录

不要完整复制项目目录树。

只记录理解和修改项目真正需要知道的结构。

---

## 运行与开发方式【必选】

记录开发当前项目必须知道的运行方式。

根据实际情况包括：

* 依赖安装
* 本地启动
* 构建
* 必要环境准备
* 必要环境变量
* 多应用启动顺序
* 特殊开发工具

如果命令已有稳定脚本，应优先引用真实命令。

---

## 验证策略【必选】

记录当前项目实际可用的验证方式，以及不同修改对应的最低验证要求。

根据项目情况包括：

* 单元测试
* 集成测试
* E2E
* lint
* 类型检查
* 构建
* 文档检查
* 其他项目特有验证

统一原则：

* 优先运行与当前修改直接相关的最小验证集合；
* 修改公共能力、基础设施或跨模块行为时扩大验证范围；
* 不为了让测试通过而改变本来正确的业务行为；
* 无法执行某项验证时，应明确说明原因；
* 不声称执行过实际未执行的验证。

---

## 项目特有规则【必选】

记录**只属于当前项目**、且需要长期遵守的开发规则。

例如：

* 模块之间的调用限制
* 特殊依赖约束
* 特殊代码组织方式
* 项目特有扩展机制
* 特殊配置处理方式
* 项目明确禁止的实现方式

团队已经存在全局规范的内容，不应在这里完整复制。

如果项目没有特殊差异，可以引用对应全局规范。

---

## 架构与分层【可选】

当项目存在明确架构或分层约束时增加。

可以记录：

* 主要架构模式
* 分层职责
* 模块依赖方向
* 跨模块调用规则
* 核心扩展点

如果项目结构简单，且“目录与模块职责”已经足够，不必单独增加本章节。

---

## 数据流转【可选】

当理解关键数据流对开发非常重要时增加。

例如：

```text
页面
→ API
→ Application/Service
→ Repository
→ Database
```

或：

```text
Producer
→ Topic
→ Consumer
→ Domain Service
```

只记录关键链路，不复制具体实现代码。

---

## 命名规范【可选】

仅记录**当前项目特有**的命名规则。

例如：

* 文件命名
* 目录命名
* 类 / 接口命名
* DTO / VO / DO 命名
* 模块命名
* 配置项命名

如果团队已有统一命名规范且当前项目没有差异，不要重复写入。

---

## 代码规范【可选】

仅记录当前项目特有的代码约束，例如：

* 注释要求
* 日志约束
* 异常处理
* 事务使用
* 缓存使用
* 依赖管理
* API 编写约束

已有团队全局规范时优先引用，不重复复制全文。

---

## Git 规范【可选】

简单说明统一规范，或当前项目存在项目级 Git 约束时增加

---

## 文档规范【可选】

仅当当前项目存在项目级文档约束时增加，例如：

* 项目文档默认位置
* 特殊文档目录
* 文件命名方式
* 项目特有文档维护要求

团队已有全局文档规范时，不重复复制。

---

## 禁止事项【可选】

当项目存在明确、长期有效的禁止行为时增加。

例如：

* 禁止跨层直接调用
* 禁止修改生成文件
* 禁止直接依赖某模块
* 禁止在特定目录新增业务代码
* 禁止绕过既有扩展机制

禁止事项必须有明确依据，不根据个人偏好随意增加。

---

## 常见风险【可选】

记录在该项目中具有长期价值、容易反复出现的风险。

例如：

* 某模块修改容易影响多个应用
* 某配置存在环境差异
* 某目录由代码生成
* 某操作容易造成兼容性问题

不要把一次 Bug 或一次调试经历直接记录为长期风险。

只有确认具有重复发生价值时才保留。

---

## 子级 AGENTS.md【可选】

如果项目使用子目录级 `AGENTS.md`，可以在根文件中说明：

* 哪些目录存在局部规则；
* 为什么需要独立规则；
* 根规则与子级规则如何配合。

子级 `AGENTS.md` 只记录局部新增或覆盖规则，不复制根级完整内容。

---

## 五、最小必选结构

对于普通项目，至少建议维护：

```md
# AGENTS.md

## 项目概述

## 技术栈

## 目录与模块职责

## 运行与开发方式

## 验证策略

## 项目特有规则
```

其他章节均根据项目实际情况增加。

如果某个必选章节当前确实不适用，应删除该章节，而不是保留空标题或填写 `无`、`N/A` 等占位内容。

---

## 六、核心原则

维护 `AGENTS.md` 时始终遵循：

> **只记录 Agent 在未来执行其他任务时仍然需要知道的信息。**

如果一条信息只对当前任务有价值，就不应该进入 `AGENTS.md`。

如果一条规则已经由团队全局规范统一定义，当前项目没有差异，就应该引用而不是复制。

如果某项规则可以通过当前项目稳定确认，应以当前项目事实为准，不依赖历史记忆。
