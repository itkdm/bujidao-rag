# candidate/

## 目录定位

`candidate/` 是可审查、可验证、最终必须退出的候选知识队列。它只接收可能成为长期知识、但证据、范围或确认条件尚未闭环的内容，不是草稿箱、资料库或 TODO 集合。

候选内容不是当前项目事实。Agent 只有在核对知识缺口、冲突或待确认结论时才读取本目录，正常实现任务不得把候选结论当作默认依据。

## 目录映射

已能判断目标范围的候选按拟晋升位置建立镜像：

```text
knowledge/candidate/main/<relative-path>
→ knowledge/main/<relative-path>

knowledge/candidate/applications/<appCode>/<relative-path>
→ knowledge/applications/<appCode>/<relative-path>
```

`main/` 与 `applications/` 是必备入口。只有连目标范围都无法判断时，才按需建立 `unclassified/`；完成分类后必须迁出，不得把它维护成长期收件箱。

目录和文件名表达候选的目标身份。不得再建立 `pending/`、`reviewed/`、`approved/` 等状态目录，也不为候选文档添加 YAML Front Matter。候选被确认后应退出本目录，而不是继续保留一个“已批准”副本。

每级目录中的 `README.md` 与 `INDEX.md` 是保留的导航基础设施，不属于候选正文、不参与目标镜像和晋升。候选知识不得使用这两个文件名；如果需要调整 candidate 导航规则，应直接审查导航文件，涉及未来方案时进入 Change。

## 应包含的内容

- 从代码、配置、运行现象或现有文档发现，但证据仍不完整的可复用结论。
- 多个可信来源互相冲突，尚不能确认当前真实行为的知识。
- 可能成为长期功能、规则、技术约束或基础事实，但仍需要负责人确认的内容。
- 从 `personal/<ownerCode>/` 整理出的可复用经验，尚未达到团队正式知识标准的内容。
- 初始化时无法通过当前工作区确认、但值得后续核验的应用边界或模块状态。

## 不应包含的内容

- 已由代码、配置、运行结果或负责人确认的事实：直接进入 `main/` 或 `applications/`。
- 外部官方文档、文章和上游说明：保留在 `reference/`，不能因其权威就自动成为项目事实。
- 个人排障过程、零散经验和未经整理的素材：进入对应 `personal/<ownerCode>/`。
- 准备实施的需求、技术选型、设计方案和任务计划：进入 `docs/changes/proposed/`。
- 已发生事故或 Bug 的复盘：进入 `docs/postmortem/`。
- 普通 TODO、临时提醒和无法形成可复用结论的问题：使用 Change、Issue 或任务系统。
- 已证明错误或确认不再推进的候选：移动到 `archive/candidate/`。

## 候选文件契约

每个候选文件只承载一个核心结论或一组不可拆分的紧密结论，并使用未来正式知识的文件名。正文必须包含：

1. `候选结论`：当前可能成立的结论，不能把推断写成事实。
2. `拟晋升位置`：使用代码格式写出 `knowledge/main/...` 或 `knowledge/applications/...` 的唯一目标路径。
3. `为什么仍是候选`：说明证据缺口、来源冲突或待确认责任。
4. `证据`：区分来源能证明什么、不能证明什么；没有证据时明确写出缺口。
5. `待确认问题`：列出能改变结论或归属的具体问题。
6. `验证与晋升条件`：说明如何验证，以及满足什么条件才能晋升。

不使用百分比表示可信度。直接说明缺失证据和验证条件，比主观的可信度数字更可审查。

## 流转规则

- 经当前代码、配置、可复现运行结果或负责人明确确认后，按正式知识模板重写候选专用章节。目标文件不存在时使用 `git mv` 晋升；目标文件已经存在时，把已验证内容合入正式文件，再移除或归档候选，禁止覆盖正式知识。
- 如果内容实质是待实施方案或设计取舍，转入 `docs/changes/proposed/`，不晋升为当前事实。
- 如果内容实质是外部材料或个人经验，分别转入 `reference/` 或对应 `personal/<ownerCode>/`。
- 已证明错误或不再值得推进，但仍有追溯价值时，按原相对路径移动到 `archive/candidate/`，并在正文中写明退出原因。
- 一个候选同时包含多个正式目标时，晋升前先拆分；不得把多个知识类型混进同一个正式文件。

## 正式文档中的待确认问题

正式知识可以保留与使用边界直接相关的简短复核提醒，但不应成为候选结论的长期容器。出现以下任一情况时，应抽成独立候选文件，并从正式知识链接到候选：

- 已经形成可独立验证的假设。
- 需要维护自己的证据、冲突和验证条件。
- 影响多个任务、模块或知识文件。
- 确认后会新增或实质修改正式知识。

如果问题实质是在决定“以后采用什么”，应转入 Change；如果只是每次使用前都必须核对的易变事实，则继续保留在正式知识中。

## 维护规则

- 候选内容不得参与默认事实检索；引用时必须明确标注尚未确认。
- 新建候选前先搜索正式知识、现有候选、Change 和 reference，避免重复记录。
- 每次复用候选都应顺手核对证据和验证条件；已经能够确认时及时晋升或归档。
- 根目录及每个候选子目录继续遵守 README + INDEX 协议，INDEX 只维护直接子项；这两个保留文件不得承载候选正文。
- 不为了展示目录完整性创建虚假的候选文件、appCode 或分类目录。
