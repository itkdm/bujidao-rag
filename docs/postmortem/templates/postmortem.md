## 执行摘要

一句话结论 + 影响范围。

- **怎么写**：`<问题> 因 <机制性根因> 逃过 <哪道/哪些防线>，影响 <范围>，将通过 <Guardrail 概要> 防止复发`。
- **反例**：「修复了一个 Bug」（这是 Change 的写法，不是 Postmortem）。

## 影响与发生了什么

- 发生了什么（客观事实，不评判）
- 影响范围（环境 / 数据 / 用户 / 发布版本 / 时长）

## 时间线（推荐，可简化）

- 大型事故：发布 → 报错 → 告警 → 定位 → 回滚 → 根因确认（带时间点）
- 普通 Bug：发现 → 初步误判 → 排查 → 根因确认 → 修复
- **怎么写**：只列关键节点，不必精确到秒；目的是暴露「防线在哪一刻本应响亮失败却没响」。

## 根因

真正根因。重点描述**机制**，而非某行代码。

- **怎么写**：说明「为什么系统允许了这件不该发生的事」，指向设计/流程/工具缺口，而非个人失误。
- **反例**：「张三忘了加锁」（这是表象，不是机制根因）。

## 为什么逃过防线

> 本块是 Postmortem 的灵魂：逐道防线说明「为什么它没工作」，而不是笼统说「测试不足」。

### 测试

- 为什么单元测试 / 集成测试没发现（是没覆盖该场景？还是测错对象？还是断言太弱？）

### 评审

- 为什么 Code Review 没发现（是缺检查清单？还是变更太大看不过来？还是 reviewer 不具备该领域知识？）

### 工具 / CI

- 为什么 CI / 类型系统 / 静态检查没阻止（是规则缺失？还是该检查未接入？还是告警被忽略？）

### 流程 / 规范

- 为什么现有规范 / 流程没覆盖（是 AGENTS.md 没写？还是写了但无人 enforce？）

## 防线（Guardrails）

> 不要写「以后要更细心 / 加强测试 / 提高责任心」——这类等于没写。
> 核心思想：**不要依赖人记住事故，要让工程系统记住事故。** 每条 Guardrail 必须可落地、可验证、链接到具体 Change。

- **Guardrail 1（Test）**：<新增/修改什么测试，验证什么机制>
- **Guardrail 2（CI）**：<CI 如何强制运行该测试 / 检查>
- **Guardrail 3（Rule）**：<AGENTS.md / 规范需补充什么具体约束>
- **Guardrail 4（Tooling）**：<脚本 / 静态检查 / lint 规则>

- **怎么写**：每条标注类型（Test/CI/Rule/Tooling）+ 具体动作 + 对应 Change 路径。
- **反例**：「增加更多测试」（无对象、无验证、无人负责）。
