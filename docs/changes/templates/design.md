# Design: <对应 Change 标题>

为满足 Change / Spec，最终采用的技术方案。

> 以下章节均按实际设计需要保留；不存在对应设计内容时直接删除该章节，**不要求补齐所有章节**，避免模板垃圾。
> 本文件不复制 Spec，不写成任务清单，也不保留大量未收敛的调研过程。
> 若存在 `spec.md`，以其作为详细行为规格来源；若存在 `research.md`，其结论可作为设计输入（两者均为可选）。

## 设计背景

- 设计背景与约束（来源：Change 的「问题 / 范围」、Spec 的「约束」、Research 的「结论」）
- **怎么写**：一段话交代为什么这样设计，引用上游输入，不重复展开。

## 架构与组件

- 关键组件及其职责、相互依赖
- **怎么写**：列出新增/修改的组件及边界；可配文字结构图。

## 数据流

- 主要数据流（请求、事件、状态变更如何流转）

## 数据模型

- 关键数据模型（表、字段、关系变更；仅列与设计决策相关的）

## API / 接口 / 契约

- 对外契约（API、配置项、消息事件、接口签名）
- **怎么写**：写契约本身（入参/出参/语义），不写实现代码。

## 状态与生命周期

- 涉及的状态与生命周期变化

## 错误处理

- 错误处理策略（失败重试、降级、回滚、用户提示）

## 并发与一致性

- 并发与一致性考量（锁、事务边界、幂等）

## 安全与性能

- 安全与性能考量（鉴权、越权、耗时、资源占用）

## 关键决策

- 关键决策点（设计中的「选 A 不选 B」结论，含理由）
- **怎么写**：每条决策对应一个权衡；与 Research 结论呼应。

## 取舍与影响

- 取舍与后果（放弃了什么、带来了什么代价）

## 迁移与兼容性

- 迁移与兼容性处理（数据迁移、接口兼容、灰度策略）

---

> 边界提醒：本文件写「怎么实现」，不写「为什么需要」（那是 Change/Spec）；不写「怎么一步步做」（那是 Plan）；不写「还不确定要不要这样」（那是 Research）。
