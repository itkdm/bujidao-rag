# 芋道系列识别指南

仅当目标工作区使用或疑似使用芋道系列项目时读取。目标是识别真实形态，不是推荐某个版本或模块。

## 1. 后端形态

### 单体版

常见证据组合：

- 根 Maven 工程聚合 `yudao-dependencies`、`yudao-framework`、`yudao-server` 和若干 `yudao-module-*`
- 单一 `yudao-server` 作为主要启动与装配入口
- 业务模块以 Maven module 参与同一应用构建

知识目录通常只建立一个后端应用目录；内部 `yudao-module-*` 作为 module/base 索引，不自动建立独立 appCode。

### 微服务版

常见证据组合：

- 存在 Spring Cloud、网关、注册配置中心或多个独立服务启动入口
- 多个服务可以独立构建、运行或部署
- 服务之间存在 RPC、HTTP 或消息调用关系

知识目录应按真实部署边界建立多个 appCode 目录。不要把微服务仓库整体伪装成一个单体应用，也不要仅凭目录名认定服务已部署。

### 版本与 Java 基线

必须从当前 `pom.xml`、BOM、Wrapper、构建脚本和源码命名空间核对：

- 上游分支或版本
- JDK 版本
- Spring Boot / Spring Cloud 版本
- `javax.*` 或 `jakarta.*` 基线
- 当前工程 revision

不得从模板示例继承版本。

## 2. 模块启用判断

按三层证据核对：

1. 聚合构建：根 `pom.xml` 中未注释的 `<module>`。
2. 运行装配：`yudao-server` 或各服务 `pom.xml` 中的实际依赖。
3. 运行配置：对应 Profile、配置项、数据库脚本和启动入口。

只有目录存在、官方文档存在或根 POM 中被注释，不视为启用。

初始化知识时应分别记录：

- 已启用并参与运行
- 参与构建但运行状态待核对
- 目录存在但未启用
- 目标项目自行新增的模块

## 3. 前端形态

芋道系列可能出现多种前端，应从 `package.json`、依赖和源码入口识别，例如：

- Vue3 + Element Plus 管理后台
- Vben 管理后台
- Vue2 管理后台
- Admin Uniapp 或其他移动端

每个可独立构建和部署的前端通常建立独立 appCode 目录。不要因为官方文档列出某个前端，就认为目标仓库采用了它。

至少核对：

- package name、版本和包管理器
- Vue / Vite / UI 框架版本
- 实际路由、API、权限和环境配置入口
- 与后端应用的真实调用关系

## 4. 芋道项目初始化决策清单

以下内容是初始化时要从目标工作区核对、必要时向用户确认的决策点，不是当前示例项目的“待确认事实”，也不要长期散落在正式知识中：

- 应用与模块：是否新增独立模块，实际启用哪些上游模块，模块、包名与部署边界如何划分。
- API 与模型：Admin/App API 前缀、Controller 包、响应结构，以及 Admin/App VO 是否隔离。
- 数据与租户：数据库类型、表前缀、逻辑删除、多租户字段、数据权限范围和缓存一致性策略。
- 安全与权限：是否沿用上游 RBAC，App 端是否使用独立权限体系。
- 异步能力：启用的 MQ 类型、消息幂等策略，以及本地环境是否运行 Job。
- 构建与配置：本地 Profile、构建范围、敏感配置和外部密钥管理方式。
- 错误治理：新增模块的错误码范围、错误文案风格与日志边界。

能够由代码、配置或运行结果证明的，直接写入正式知识；形成独立但未闭环的事实假设时写入 `candidate/`；需要决定未来采用什么时建立 Change。初始化当下无需决定、也不影响当前知识准确性的项目，不要制造占位记录。

## 5. 官方参考资料

目标项目使用芋道时，可以保留完整官方文档作为上游证据库，因为不同用户可能启用不同模块；但路由和正式应用知识只能指向当前项目相关部分。

目标项目不使用芋道时：

- 不把芋道参考资料设为默认知识入口
- 已确认它只是模板附带内容时，可以移除或替换
- 归属不明或包含用户补充内容时，先请求确认

## 6. 初始化输出重点

芋道项目初始化报告必须明确列出：

- 单体或微服务形态
- JDK、框架和工程版本
- 参与构建与运行的模块
- 未启用但目录存在的模块
- 采用的前端版本
- 仍需用户确认的模块或部署边界
