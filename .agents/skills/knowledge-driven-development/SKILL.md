# 知识驱动开发

让日常研发任务先经过项目知识路由，再以当前代码事实完成设计、实现、验证和知识回写。知识库提供上下文和约束，不替代对真实实现的检查。

## 适用边界

本 Skill 适用于会理解、评审或改变项目实现的研发任务。纯知识库初始化或重新识别项目边界使用 `knowledge-docs-initializer`；不涉及产品实现的知识录入、晋升、归档、路由修复或研发文档治理使用 `knowledge-docs-maintenance`；其他纯文案任务不使用本 Skill。

本 Skill 只编排项目上下文与研发闭环。具体语言、框架、测试、浏览器或部署能力仍使用当前环境中适用的工具和 Skill；不得因为使用本 Skill 扩大用户授权范围。

## 工作流程

### 1. 建立任务上下文

开始时确认当前工作区、Git 状态、用户目标和允许修改的范围。根级 `AGENTS.md` 是自动加载规则入口；首次接触当前项目时完整读取 `knowledge/README.md`，每个具体研发任务都完整读取 `knowledge/ROUTING.md`。

先判断任务是只读的理解、诊断或审查，还是用户已经授权的实现修改。只读任务只检查并报告证据，不修改代码、知识或研发文档；变更任务才进入实施与回写。

README 或 ROUTING 缺失、不可读或仍含未替换模板标记时，不得凭记忆编造知识路由。若当前代码和 AGENTS 足以支持用户已经授权的局部任务，可以在明确报告“未加载到项目知识约束”后按代码事实继续；若缺失知识会实质影响应用边界、业务规则或设计决策，则停止实施并建议先使用 `knowledge-docs-initializer` 完成初始化。

不得默认读取整个知识库。根据 ROUTING 识别目标应用、任务意图和停止条件，只加载完成当前任务所需的最小文件集合。

### 2. 加载最小知识

优先服从 ROUTING 给出的精确读取路径和停止条件。ROUTING 没有覆盖当前意图，或应用边界、启用状态仍不明确时，再按以下顺序补充定位：

1. 目标应用的 `knowledge/applications/<appCode>/INDEX.md`，必要时再读取应用总览。
2. 与任务直接相关的 `base/`、`feature/`、`rule/`、`tech/` 文件。
3. ROUTING 指向的跨应用 `knowledge/main/` 规范。
4. 当前任务直接关联的 `proposed` Change，以及仍代表当前决策的 `implemented` Change；不把 `rejected` 或 `archived` 作为默认事实来源。

只有需要核对上游能力或外部证据时才读取 `reference/`；`candidate/` 不能作为已确认事实使用；`personal/` 和 `archive/` 不参与默认开发路由。

加载后形成简短的任务约束清单，至少明确：目标应用、真实代码入口、必须遵守的规则、当前已知风险和最低验证要求。无需为了记录这份临时清单创建新文件。

### 3. 核对当前实现

编辑前检查与任务直接相关的构建清单、入口代码、配置、测试和调用链。目录存在、上游文档、历史知识或依赖声明都不能单独证明能力已经启用。

知识与代码不一致时，不要静默选择其中一方：

- 先通过当前代码、运行配置、有效 Change 和用户明确确认判断哪一方代表预期事实。
- 代码偏离预期时按任务修复代码。
- 知识已经失效时在本次授权范围内同步更新知识。
- 暂时无法确认且可能长期复用的结论按 ROUTING 进入 `candidate/`，不得写入正式知识。

### 4. 判断研发文档

任务可能改变系统行为、契约、架构、模块边界、数据、配置，或包含以后需要追溯的重要取舍时，先读取 `docs/changes/README.md`，再判断是否创建或更新 Change。普通机械修改不为目录完整而创建 Change。

只有问题已经发生，并且可能达到系统性防线缺口的复盘条件时，才读取 `docs/postmortem/README.md` 并判断是否创建 Postmortem。不得把修复方案正文重复写进 Postmortem。

### 5. 实施或审查与验证

变更任务按照用户范围、AGENTS、已加载知识和当前代码实施最小完整修改；只读任务保持非修改性并输出证据充分的审查或诊断结论。不得仅凭知识文档猜测接口、模块、数据结构或启用状态，也不得为了符合过期文档而破坏正确实现。

验证顺序为：

1. 运行与修改直接相关的最小检查。
2. 公共能力、基础设施、契约或跨模块行为变化时扩大验证范围。
3. 合并 AGENTS 与已加载知识中的专项检查清单。
4. 无法执行的验证明确说明原因，不得声称已经运行。

### 6. 闭环知识与文档

变更任务完成后判断实际变化是否产生未来任务仍需知道的内容；只读任务只报告建议，不直接回写：

- 已确认且长期有效的事实、规则或实现机制，更新 ROUTING 指定的正式知识。
- 证据或范围未闭环但可能长期复用的结论，写入 `candidate/`。
- 一次研发决策与实施结果，更新对应 Change。
- 没有长期复用价值的临时过程，不写入知识库。

修改 knowledge 或 docs 时同步更新受影响的 INDEX、ROUTING 和相对链接，运行 `python knowledge/scripts/validate.py`。若项目规则要求独立审查，必须在提交前完成并合理处理意见。

## 交付要求

最终说明应覆盖：实际修改、关键依据、验证结果、未执行验证、知识或 Change 的更新，以及仍需确认的候选结论。不要用“已按规范处理”代替具体证据。

## 不可违反的边界

- 不把上游示例、reference、candidate、personal 或 archive 当作当前实现事实。
- 不把整个知识库无差别加载进上下文。
- 不为每次代码修改机械创建知识、Change 或 Postmortem。
- 不复制已有规范正文到 Skill；规则变化应更新其知识权威来源。
- 不在文档中记录密码、Token、API Key、私密通信、个人隐私或本机专属凭据。
